# Vault Security Audit — 2026-05-06

## Scope

- `Wormhole_miniapp/utils/vaultCrypto.js`
- `Wormhole_miniapp/pages/vault/vault.js` (skim — caller of vaultCrypto)
- `Wormhole_backend/app/api/vault.py`
- `Wormhole_backend/models/vault.py`
- `Wormhole_backend/schemas/vault.py`

## Methodology

Static review against OWASP cryptographic-storage and access-control baselines.
The Wormhole vault is a **per-space shared encrypted store** (all members of a
space share one passphrase). All encryption / decryption happens client-side in
the WeChat MiniProgram; the server only stores ciphertext blobs and the
KDF parameters needed to re-derive the key from the user-supplied passphrase.

## Threat model assumed by the design

1. The OSS bucket / database operator MUST NOT be able to read vault contents.
2. A non-member of the space MUST NOT be able to read or download vault items.
3. All members of a space share the vault passphrase — they trust each other
   with the contents. (This is the *design intent*; cross-member confidentiality
   is NOT a goal.)
4. An attacker who steals the database (or just the `/vault/status` response
   for a space they belong to) gets the salt + check ciphertext and can
   mount an offline brute-force against the passphrase.

## Findings

### F1. Key Derivation — At Risk (Important)

- **Status:** At Risk. Iteration count is below current OWASP recommendation.
- **Evidence:**
  - `Wormhole_miniapp/utils/vaultCrypto.js:4` — `const DEFAULT_ITERATIONS = 30000;`
  - `Wormhole_miniapp/pages/vault/vault.js:5` — `const CHECK_ITERATIONS = 30000;`
  - `Wormhole_backend/schemas/vault.py:23` — `kdf_iterations: int = Field(default=30000, ge=10000, le=120000)`
  - `Wormhole_backend/models/vault.py:14` — `kdf_iterations = Column(Integer, default=30000)`
  - Salt: `vaultCrypto.js:287` — 16 random bytes per vault via `randomBytes(16)`. Unique per vault. OK.
- **Impact:** OWASP ASVS 2024 recommends PBKDF2-SHA256 ≥ 600k iterations
  (or Argon2id). At 30k iterations a modern GPU can attempt ~10^7
  passphrases/sec; an 8-char alphanumeric passphrase falls in hours. The
  `/vault/status` endpoint returns the salt + check ciphertext to any space
  member, so the brute-force target is reachable for a malicious insider or
  anyone who exfiltrates a single status response. The page enforces only an
  8-character minimum (`vault.js:212`).
- **Recommended Fix:** Raise `DEFAULT_ITERATIONS` and the schema floor for
  *new* vaults to 100,000 (modest minimum given pure-JS PBKDF2 runs on a
  WeChat MiniProgram device, which is CPU-bound). Keep the stored
  `kdf_iterations` per-row so existing 30k vaults still unlock; only new
  init requests are constrained. **Fixed in this commit** — see Remediation.

### F2. Encryption Algorithm — OK

- **Status:** OK (custom encrypt-then-MAC AEAD, not AES-GCM as the checklist
  asks, but cryptographically equivalent when implemented correctly).
- **Evidence:**
  - `vaultCrypto.js:3` — `const CIPHER_ALGO = 'chacha20-hmac-sha256';`
  - `vaultCrypto.js:272-276` — `sealBytes` runs ChaCha20 then HMAC-SHA256
    over `(context || nonce || ciphertext)`. Encrypt-then-MAC with domain
    separation by context string (`vault-check`, `vault-file`, `vault-name`,
    `vault-meta`).
  - `vaultCrypto.js:278-284` — `openBytes` recomputes MAC, compares with
    constant-time `safeEqual` (line 252-259), aborts before decrypting on
    mismatch. Correct order.
  - Key split: `vaultCrypto.js:262-269` — PBKDF2 emits 64 bytes;
    first 32 are encryption key, next 32 are MAC key. Independent keys for
    enc and MAC. Correct.
- **Impact:** No known practical attack. ChaCha20 + HMAC-SHA256 EtM is
  used in TLS (RFC 7905) and is sound. The custom JS implementation is
  the risk surface — see F2.1 below.
- **Recommended Fix:** Long-term, prefer `crypto.subtle` (Web Crypto)
  AES-256-GCM where available on WeChat. For now, **OK as-is**.

#### F2.1. Pure-JS Cryptographic Primitives — At Risk (Minor)

- **Status:** At Risk.
- **Evidence:** `vaultCrypto.js:118-160` (SHA-256), `:162-174` (HMAC),
  `:208-237` (ChaCha20 block) are hand-rolled in JavaScript. No WebCrypto
  fallback path is taken when `crypto.subtle` is available.
- **Impact:** Side-channel resistance is weaker than native primitives
  (no constant-time guarantees from the JIT). Performance cost forces
  the iteration count down (see F1). Bugs in the implementation would
  not be caught by test vectors today (none exist).
- **Recommended Fix:** Add KAT (known-answer-test) vectors for SHA-256,
  HMAC, PBKDF2, and ChaCha20 in a Jest-style harness. Fall back to
  `crypto.subtle` when present. **Deferred** — follow-up task.

### F3. IV / Nonce Reuse — OK

- **Status:** OK.
- **Evidence:**
  - `vaultCrypto.js:288` — `randomBytes(12)` for vault check nonce.
  - `vaultCrypto.js:323` — `randomBytes(12)` per `encryptText` call (used
    for name and meta encryption).
  - `vaultCrypto.js:344` — `randomBytes(12)` for each file body.
  - `randomBytes` (`vaultCrypto.js:93-112`) sources `crypto.getRandomValues`
    or `wx.getRandomValues`; rejects if neither is available — never falls
    back to `Math.random`. Good.
- **Impact:** None. 96-bit random nonces are safe up to ~2^32 messages
  per key by the birthday bound. A single vault is unlikely to exceed
  this.
- **Recommended Fix:** None.

### F4. Error-Password Rate Limiting — At Risk (Important)

- **Status:** At Risk.
- **Evidence:**
  - The server never sees the passphrase. Decryption + check-blob
    verification happens entirely in `unlockVault` (`vaultCrypto.js:304-320`).
    Therefore the server has no per-user "wrong password" counter to
    enforce.
  - `Wormhole_backend/app/api/vault.py:65-77` — `GET /vault/status`
    returns `key_salt`, `kdf_iterations`, `check_nonce`, `check_ciphertext`,
    `check_tag` to any space member. **No `@limiter.limit` decorator** on
    this endpoint. Compare with `app/api/auth.py:44` which limits login
    to `10/minute`.
  - `vault.py:80-111` (`POST /init`), `:114-128` (`GET /files`), `:131-210`
    (`POST /upload`) — none rate-limited.
- **Impact:** A space-member attacker can scrape `/vault/status` once
  (one HTTP call) and then run an *offline* PBKDF2 brute-force attack
  with no further server contact. Online rate-limiting cannot defend
  against an offline attack — that's why F1 (raise iteration count) is
  the primary mitigation. However, rate limiting `/vault/status` and
  `/vault/init` still helps:
  1. Slows automated scraping if an account is compromised.
  2. Prevents abuse of `/init` and `/upload` for resource exhaustion.
- **Recommended Fix:**
  1. Add `@limiter.limit("30/minute")` to `/vault/status` and `/vault/files`.
  2. Add `@limiter.limit("10/minute")` to `/vault/init`, `/vault/upload`,
     `/vault/files/{id}/download`, `DELETE /vault/files/{id}`.
  3. Long-term: add a server-side "decrypt attempt counter" by having the
     client report unlock failures to a rate-limited endpoint, then lock
     out for N minutes after M failures. **Deferred** — follow-up task.

  **Fixed in this commit** — items 1 and 2.

### F5. Password Change Handling — Vulnerable (Important, design gap)

- **Status:** Vulnerable to data-loss (not confidentiality), important
  UX gap.
- **Evidence:**
  - `vault.py:80-111` — `init_vault` short-circuits on existing vault:
    ```python
    if existing:
        return _build_status(existing)
    ```
    There is no `PUT /vault/rotate-passphrase` or equivalent endpoint.
  - `vaultCrypto.js` exports no `rotateVaultKey` / `reEncryptItems`
    helper.
  - The miniapp page `vault.js` has no "change password" UI.
- **Impact:** Once the passphrase is set, it cannot be rotated. If a
  user suspects the passphrase was leaked, the only options are:
  (a) abandon the vault and create a new space, or
  (b) operator-level deletion of the `vault_spaces` row, which silently
       leaves all `vault_files` rows orphaned (the `space_id` FK still
       resolves, but no key derivation parameters exist; the client
       will treat the vault as uninitialized and may re-init,
       overwriting the row but not the orphaned files).
  No backup-prompt flow exists — a new vault will not re-encrypt
  existing files.
- **Recommended Fix (deferred to follow-up task):**
  1. Add `POST /vault/rotate` that takes the old `key_salt` /
     `check_*` (verified by the client unlocking it) plus new
     `key_salt` / `check_*`, and re-encrypts each `vault_files` row's
     `encrypted_name` / `encrypted_meta` with the new key (the file
     bodies in OSS need re-uploading too — heavy, do it as a paginated
     background job).
  2. Add a UI prompt on rotate: "All files will be re-encrypted; do
     not close the app. We'll keep your old encrypted copies for 7
     days as a fallback."
  3. Document this gap in the README until rotation lands.

  **Documented as a known limitation; fix deferred.**

### F6. Server-Side Field Visibility — OK by design, with one Important caveat

- **Status:** OK by design (vault is per-space shared) with one access-
  control hardening opportunity (signed-URL leakage window).
- **Evidence:**
  - `vault.py:65-77` — `vault_status` calls `verify_request_user` then
    `require_space_member`. Non-members get 403. OK.
  - `vault.py:80-111` (init), `:114-128` (list), `:131-210` (upload),
    `:213-232` (download), `:235-268` (delete) — all gated by
    `verify_request_user` + `require_space_member`. OK.
  - `verify_request_user` (`app/security.py:266-314`) requires
    token-or-header identity; query-string `user_id` is rejected on HTTP
    routes (covered by `tests/test_security_query_fallback.py`). OK.
  - **However**, `vault.py:229` — `get_vault_download` returns a signed
    OSS URL with the bucket-level default expiry. Once issued, the URL
    is valid for whoever holds it for the lifetime of the signature,
    even if the user is removed from the space the next second. The
    URL also conveys access to the *raw ciphertext*, not plaintext,
    so the worst case for confidentiality is still bounded by the
    passphrase — but a freshly removed member retains read access to
    every file they pre-signed-URL'd until expiry.
  - `vault.py:235-268` — `delete_vault_file` allows ANY space member
    to delete ANY file in the vault, including files uploaded by other
    members. This appears to be intentional for a shared store, but
    is worth surfacing.
- **Impact:**
  - Status / list / upload / download / delete are correctly gated.
    A non-member returns 403. **No cross-space data leakage.**
  - A removed member who pre-fetched a download URL retains read
    access to the ciphertext until the URL expires.
  - A misbehaving member can erase a colleague's uploads without
    confirmation.
- **Recommended Fix:**
  1. Make signed URLs short-lived (≤ 5 min) and scoped to the
     calling user. **Deferred** — depends on `app/storage/oss.get_signed_url`
     accepting an expiry parameter.
  2. Optionally restrict `DELETE /vault/files/{id}` to the original
     uploader OR space owner. **Deferred** — product decision.
  3. Add an audit log entry on every vault read (currently we only
     log `vault_init`, `vault_upload`, `vault_delete`). **Deferred.**

**Critical findings:** 0. The server-side access controls are correctly
wired through `verify_request_user` + `require_space_member`; no
cross-space leakage was found.

**Important findings fixed in this commit:** F1 (raise iterations), F4
(rate-limit vault endpoints).

**Important findings deferred:** F5 (passphrase rotation — needs UX +
re-encryption pipeline; substantial follow-up).

**Minor findings:** F2.1, F6.1, F6.2 — track in backlog.

## Remediation Plan

### Now (this commit)

1. **F1:** Bump `DEFAULT_ITERATIONS` to 100,000 in `vaultCrypto.js`,
   `CHECK_ITERATIONS` to 100,000 in `pages/vault/vault.js`, schema floor
   to 100,000 in `schemas/vault.py`, default in
   `models/vault.py` to 100,000. Existing rows unaffected — they keep
   their stored `kdf_iterations` and continue to unlock with 30k.
2. **F4:** Add `@limiter.limit(...)` to all vault endpoints.
3. Add a regression test
   (`tests/test_vault_access_control.py`) covering:
   - `/vault/status` returns 403 for non-member.
   - `/vault/files` returns 403 for non-member.
   - `/vault/init` returns 403 for non-member.

### Next sprint (follow-up tasks)

- **F5:** Design + ship `POST /vault/rotate` and miniapp UI.
- **F6.1:** Plumb expiry into `get_signed_url`, make vault downloads use ≤ 5 min.
- **F6.2:** Restrict `DELETE` to uploader or space owner.

### Backlog (nice-to-have)

  Try `crypto.subtle` fast-path on platforms that expose it.
